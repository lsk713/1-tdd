# 포인트 동시성 제어 분석 보고서

## 1. 문제 정의
- `charge/use`는 `조회(select) -> 계산 -> 갱신(update) -> 이력(insert)`의 다단계 작업입니다.
- 동시 요청이 들어오면 조회 시점의 잔액이 겹쳐서 **lost update**가 발생할 수 있습니다.
- `/database` 패키지 구현체(`HashMap`, `ArrayList`)는 수정 금지이므로, 서비스 계층에서 제어해야 합니다.

## 2. 고려한 제어 방식

### 방식 A. 동기화 없음
- 장점: 구현이 가장 단순
- 단점: 동시성 오류가 발생할 가능성이 높아 요구사항 미충족

### 방식 B. 사용자별 Lock
- 장점: 서로 다른 사용자 요청은 병렬 처리 가능
- 단점: 현재 `PointHistoryTable`이 전역 `ArrayList`를 사용하므로 사용자별 Lock만으로는 완전한 thread-safety를 보장하기 어려움

### 방식 C. 전역 Lock (채택)
- 장점: 모든 포인트 연산을 한 번에 하나씩 처리해 데이터 정합성을 단순하고 확실하게 보장
- 단점: 처리량(throughput)이 낮아질 수 있음

## 3. 채택 설계
- `PointService` 내부에 전역 monitor(`lock`)를 두고, 조회/충전/사용/이력조회에서 임계영역을 사용합니다.
- `use`는 임계영역 내에서 잔액 검증을 수행해 부족 시 즉시 예외를 발생시킵니다.
- 성공 케이스에서만 `PointHistoryTable.insert(...)`를 수행해 실패 시 부수효과를 막습니다.

## 4. 트랜잭션 경계
- `charge`
  1. 현재 포인트 조회
  2. 잔액 계산 후 업데이트
  3. CHARGE 이력 저장
- `use`
  1. 현재 포인트 조회
  2. 잔액 검증(부족 시 실패)
  3. 잔액 차감 업데이트
  4. USE 이력 저장

두 연산 모두 서비스 임계영역 기준으로 원자적으로 처리됩니다.

## 5. 검증 전략
- 단위 테스트(`PointServiceTest`)
  - 포인트 조회
  - 포인트 내역 조회
  - 충전 성공
  - 사용 성공
  - 잔고 부족 실패 및 부수효과 없음
- 동시성 통합 테스트(`PointConcurrencyIntegrationTest`)
  - 동시 충전 누적 정확성 검증
  - 동시 사용 시 초과 사용 방지 검증

## 6. 한계와 확장 방향
- 현재 방식은 단일 애플리케이션 인스턴스 기준으로 안전합니다.
- 다중 인스턴스(분산 환경)에서는 Redis 분산 락, DB row-level lock, 메시지 큐 직렬화 등의 별도 전략이 필요합니다.
